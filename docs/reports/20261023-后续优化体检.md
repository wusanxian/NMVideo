## 2. 真实缺口（按优先级，均带代码证据）

### P0-1 H3 是默认引擎，但从未实机跑过【最高风险】

- 证据：`engines/h3.py:1-30` 明确"不支持 CPU"；本机 `torch_cuda_available=False`，权重未下载。
- 影响：v0.1.3 起默认引擎就是 h3。新用户安装 → 下载 139GB → 首次加载 2~5 分钟 → 出片，**这条唯一主路径全部只有 mock 支撑**。17n+5 吸附、32 对齐、短镜头截断重采样、fp8、block offload、双 workflow 切换，全部可能在实际显存/版本上炸。
- 建议：做一次 N 卡实机验收（512×288 / 124 帧起步，记录显存峰值），把结果写进 `docs/reports/`。同时给 H3 加**首次运行自检**：模型文件清单校验 + 一次极短试跑（约 30 秒）后才允许入队，避免用户排 20 分钟后在去噪阶段失败。
- 验收：实机一次成功出片 + 峰值显存记录 + 自检失败时给出明确缺项提示。

### P0-2 自动更新全链路未验证

- 证据：`desktop/main.js:317-323` 已接 electron-updater 事件链；但 0.1.4→0.1.5 未在实机点过"检查更新"。
- 影响：发版再多也送不到老用户手上，且安装包未签名会弹"未知发布者"。
- 建议：拿 0.1.4 安装包在干净机器/虚拟机上升级一次，记录 `update-available → downloaded → 重启生效` 全过程。
- 验收：old version 点检查更新 → 新版本启动成功 → 版本号变为 0.1.5。

### P0-3 测试不在仓库里，新机器无法回归

- 证据：`.gitignore:78-80` 排除 `backend/tests/`、`desktop/tests/`、`test_*.py`；`git ls-files backend/tests` 为空。本地 36 个测试文件（402 用例）**只存在于本机**。
- 影响：换机、协作、CI 全部无法复现质量门禁；一次磁盘事故就丢光 400 个用例。
- 建议：把测试目录收回仓库（体积可控，纯代码），或单独 `tests` 分支 + submodule；再加 GitHub Actions 跑 `pytest -q -m "not slow"`。
- 验收：`git clone` 后 `pytest` 直接可跑；CI 绿灯。

### P1-1 H3 生成期间无法取消

- 证据：`engines/h3.py:389-394` 注释"modular blocks 没有 step 回调：生成期间无法中断，只能事后检查"；进度从 0.48 直接跳 0.9。
- 影响：124 帧在 16GB 卡上可能十几分钟，用户点取消没反应，只能杀进程 → 任务状态脏。
- 建议：把 H3 推理放**子进程**（`multiprocessing` / 独立 worker），主进程持句柄可 `terminate`；顺带解决显存泄漏与崩溃隔离。次优方案：UI 明示"该引擎不可中断，预计 X 分钟"。

### P1-2 换 workflow 要重载 2~5 分钟

- 证据：`engines/h3.py:183-190` 单例按 workflow 缓存，切换即释放重建。
- 影响：用户交替做"纯文生"和"首尾帧"分镜时，每个镜头都可能付一次加载成本。
- 建议：先验证 `fl2va` 在无关键帧时是否等价纯文生；若成立则统一走 `fl2va` 单一 workflow，彻底消除切换。否则做双缓存（16GB 卡可能放不下，需实测）。
- 验收：交替 6 个镜头（t2v/i2v 各半），管线加载次数 = 1。

### P1-3 没有自动重试与降档重试

- 证据：全仓仅 `routers/jobs.py:121` 手工 `retry_job`；`queue_manager.py` 无 retry/backoff 逻辑。
- 影响：OOM、ComfyUI 瞬时 500、网络抖动都直接判失败，用户只能手动重试；OOM 重试还是同参数，必然再炸。
- 建议：错误分类重试——`CUDA OOM` → 自动降一档（帧数/分辨率/quality）重试 1 次并记录 `retry_downgraded`；`transient`（连接/5xx）→ 指数退避 3 次；`deterministic`（参数非法/模型缺失）→ 不重试。
- 验收：注入 OOM 异常 → 自动降档成功出片并留下记录；注入 500 → 退避 3 次后仍是明确失败。

### P1-4 SQLite 没开 WAL

- 证据：`db.py:83-85` 只有 `timeout=10` + `threading.Lock`，全仓无 `journal_mode`/`busy_timeout`。
- 影响：UI 每秒轮询队列、worker 持续写进度、导出/分镜并发，读被写锁阻塞的概率不低，表现为界面卡顿或偶发 `database is locked`。
- 建议：连接建立后 `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA busy_timeout=5000`。
- 验收：并发压测（1 writer + 8 reader 轮询 60 秒）无锁错误，P95 查询 < 50ms。

### P1-5 没有持久化日志

- 证据：`backend/app` 全目录无 `logging.basicConfig`，无日志文件；只有桌面端 stdout 转发。
- 影响：用户报"生成失败了"时，开发者拿不到任何现场；桌面端关了窗口日志就没了。
- 建议：`runtime/logs/nmsvideo-YYYYMMDD.log`，`RotatingFileHandler`（10MB×5），关键路径（入队/提交/恢复/失败/导出）结构化记录 job_id；UI 加"导出诊断包"（日志 + settings 脱敏 + 硬件探测 + 最近 20 条任务）。
- 验收：故意制造一次失败，日志含 job_id 与错误栈；诊断包可一键导出。

### P1-6 生成前无磁盘空间守卫

- 证据：仅 `hw_probe.py:98` 探利用 `shutil.disk_usage`，队列/生成入口无检查。
- 影响：模型 139GB + 成片累积，写满磁盘会在下载中途或归档阶段失败，且状态可能停在 running。
- 建议：入队前检查最小可用空间（按引擎：H3 ≈ 20GB 余量、其他 ≈ 5GB），不足直接 400 并给清理入口；对"已删除任务"的成片做孤儿清理（`last_orphan_audit` 已有基础）。
