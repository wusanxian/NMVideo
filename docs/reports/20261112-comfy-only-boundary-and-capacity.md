# 只走 ComfyUI：边界收敛、能力缺口与机型分配

日期：2026-11-12
状态：边界已定；缺口为记录项（本轮不实施）；机型矩阵为对外承诺口径

---

## 0. 一句话结论

**ComfyUI 是唯一执行底座。** 凡是不能表达成「ComfyUI 节点 + 工作流」的能力，
本产品就不提供，缺口记在本文件第 3 节，不偷偷走旁路。

配套的分配规则：**不是「能不能装」，而是「这张卡上跑这个模型，等多久、多大画布」。**
同一套 H3 权重在 8GB 卡和 24GB 卡上都能启动，但可用画布、可用步数、单段时长差一倍以上，
所以界面必须按机器分档给结论，而不是给一个「支持/不支持」。

## 1. 三层边界（先把「外部」拆清楚，否则会一刀切错）

上一轮把「H3 Image 走 FreeVideo agent REST API」写进了方案。按新边界，**那条路作废**。
但「不做外部」不等于「不用 ComfyUI 节点包」，必须分三层看：

| 层 | 内容 | 归属 | 本轮结论 |
|---|---|---|---|
| **L1 底座** | ComfyUI 本体（main.py / comfy / comfy_extras） | 我们的产品应自持 | **要收进 `runtime/comfyui`**（缺口 G1） |
| **L2 节点** | ComfyUI 的 `custom_nodes`（当前是 FreeVideo 插件，提供 `FreeVideoGenerate`） | ComfyUI 生态内的节点包 | **现阶段必需**，H3 只有它能跑（缺口 G3） |
| **L3 外部程序** | FreeVideo 桌面端、`/freevideo/agent/v1/*`、它的下载器与模型目录管理 | 第三方运行时 | **明确不做** |

判据很简单：**能不能只用 ComfyUI 的 HTTP 接口（`/prompt`、`/history`、`/view`、`/object_info`、`/system_stats`）驱动完？**
能，就在界内；需要调用别人的 REST 服务、读别人的 token 文件、依赖别人的进程，就在界外。

据此清理的既有内容：

- ❌ 「H3 Image 走 `/freevideo/agent/v1/jobs`」——作废，从模型对比文档 4.2 节改为「已否决」
- ❌ 「读 `<FreeVideo 安装根>/agent/token`」——作废
- ❌ 「按 FreeVideo 安装布局探测 `X:/AI/FreeVideo/ComfyUI`」——降级为**兼容探测**，不是产品路径
- ✅ 「`FreeVideoGenerate` 节点类名」——保留，这是 ComfyUI 侧契约，不是外部依赖
- ✅ 「向 ComfyUI 发工作流」——唯一执行方式

## 2. 当前真实能力（本机实测，非推断）

本机：RTX 4060 8GB / 32GB RAM / ComfyUI 0.34.0（929 节点），跑在自有 `runtime/comfy-venv`
（torch 2.13.0+cu130）。

| 能力 | 通道 | 状态 | 证据 |
|---|---|---|---|
| H3 文生视频 / 图生视频 / 首尾帧 / 续接 | `FreeVideoGenerate` 节点 | **可用** | 四模式预设齐备，白模链路真机跑通 |
| H3 音频同步输出 | 同上（节点带 audio 输出） | **可用** | 节点契约包含 |
| 通用 ComfyUI 工作流 | 用户自传 workflow JSON | **可用** | `comfyui` 引擎 |
| 白模（人体剪影） | `SAM3DBody_*` 节点族 | **可用** | 4060 上 25 帧首次 16s / 热态 5.5s |
| 本地生图（Qwen-Image 2.1） | 原生 ComfyUI 节点，理论可行 | **未验证** | 权重本机已有 16.11 GiB，搭过图但没跑通 |
| 本地生图（H3 Image） | — | **不可用** | 无节点、无 supported_model（见 G4） |
| 本地提示词模型 | — | **不可用** | Qwen3-VL 只是文本编码器（见 G5） |
| 进程内推理（h3_native / anime / wan22） | 不走 ComfyUI | **待下线** | 与新边界冲突（见 G7） |

> ⚠️ 记录一个必须钉住的概念区别：**「提示词模型」≠「文本编码器」**。
> 两者都叫 Qwen3-VL，但前者是替你写字的 8B VLM，后者是视频的条件输入
> （`qwen3vl_32b_minimax_h3_nvfp4_awq`，14.61 GiB）。把它俩当同一个模型算体积，
> 会直接算错磁盘门槛。

## 3. 缺口清单（本轮只记录，不实施）

排序按「不做就没法对外说支持」→「体验问题」。

| ID | 缺口 | 现在靠什么 | 只走 ComfyUI 后缺什么 | 补的成本 | 优先级 |
|---|---|---|---|---|---|
| **G1** | ComfyUI 本体未自持 | 探测外部目录（`X:/AI/FreeVideo/ComfyUI`） | 用户没装过整合包就没有 ComfyUI 可启动 | 打包源码约 50MB + 启动参数固化；`runtime/comfyui` | **P0** |
| **G2** | 没有 ComfyUI 格式的模型下载器 | `model_store` 只认 HF diffusers 布局（`model_index.json` + 目录体积） | H3 那 49.50 GiB safetensors 无法由我们安装 | 下载器加「ComfyUI 布局」分支：目标目录 + 逐文件字节 + 分片合并 | **P0** |
| **G3** | H3 节点来自 FreeVideo 插件 | 随整合包装进来 | 干净机器上 `FreeVideoGenerate` 不存在 → H3 全链路不可用 | 自持该插件（许可待确认）或自写等价节点（工程量大） | **P0** |
| **G4** | H3 Image 无 ComfyUI 入口 | 无 | 静图/角色卡拿不到 H3 侧能力 | 等插件补节点，或不用 | P1（**不补**） |
| **G5** | 本地提示词模型无节点 | 在线 LLM | 断网时无法扩写提示词 | 装 ComfyUI 的 LLM 节点 + 8.28 GiB 权重 | P1 |
| **G6** | 本地生图未验证 | 在线生图端点 | 角色四连图/场景图仍要联网 | 验 Qwen-Image 2.1 在本机 8GB 卡能否跑 4MP | **P0** |
| **G7** | 进程内推理引擎与新边界冲突 | `h3_native` / `anime` / `wan22` | 保留就是两套运行时，卸载/升级互不相关 | 标 `deprecated`，不删代码，界面隐藏 | P2 |
| **G8** | 模型目录未打通 | ComfyUI 的 `models/` 与我们的 `models/` 各存一套 | 同一个权重可能被下两遍 | 写 `extra_model_paths.yaml` 指向统一目录 | P1 |
| **G9** | 产物无磁盘配额 | 靠 `/view` 取回后自己管 | 长任务把盘写满，ComfyUI 报错难懂 | 归档目录加容量水位 + 清理策略 | P2 |

### G3 是唯一的「真阻塞」

G1、G2 是工程量问题，能做。G3 是**权利问题**：`FreeVideoGenerate` 这个节点不是 ComfyUI 官方的，
要么随包分发（要看它的许可是否允许），要么自己实现（H3 的 50 块三级放置 + 两遍加速 + 步缓存，
不是小工程）。

**在这条定下来之前，「只走 ComfyUI」在干净机器上是跑不了 H3 的。** 这句话必须写进对外说明，
不能让用户以为装了我们的包就能出片。

## 4. 机型 → 模型分配矩阵

### 4.1 判定依据（取哪台机器的数）

显存取 **ComfyUI 服务端**的（`/system_stats`），不是本机的 —— H3 跑在 ComfyUI 那台机上，
8GB 笔记本连 24GB 工作站按 8GB 限死是浪费；反过来按本机放行会让对面 OOM。
服务端探不到才退回本机口径，并在界面标「按本机估算」。

内存 / 磁盘同理：内存决定「多少块要回读磁盘」，磁盘决定「能装几个模型」。

### 4.2 四档机器

| 档 | 显存 | 内存 | 磁盘（视频-only / 全量） | 定位 |
|---|---|---|---|---|
| **S 入门** | 8 GB | 32 GB | 57.5 / 107.5 GiB | 能出片，慢；不建议叠加生图 |
| **M 标准** | 12 GB | 32 GB | 同上 | 与 S 同画布档，但步缓存命中更好 |
| **L 进阶** | 16 GB | 48 GB | 同上 | 画布翻倍、四档画质全开 |
| **XL 工作站** | 24 GB+ | 64 GB | 同上 | 高画质 + 可与生图/白模并发 |

磁盘口径（GiB）：

| 组成 | 体积 |
|---|---|
| H3 视频（int8-convrot 50 块 + 文本编码器 14.61 + 解码器 10.26 + 采样缓存 3.28） | 49.50 |
| 下载余量 + 输出 | +8.0 → **57.5** |
| Qwen-Image 2.1 Turbo（生图） | +16.11 |
| H3 Image（**当前不可用**，G4） | +20.65 |
| 本地提示词 VLM（**当前不可用**，G5） | +8.28 |
| 输出与运行期余量 | +5.0 |
| 全量合计 | **107.5** |

### 4.3 每个档位能跑什么（对外承诺口径）

| 能力 | S（8GB） | M（12GB） | L（16GB） | XL（24GB+） |
|---|---|---|---|---|
| H3 画布上限 | 1344×768 | 1344×768 | 1920×1088 | 1920×1088 |
| H3 单段帧数 | ≤430（约 17s） | ≤430 | ≤855（约 35s） | ≤855 |
| 轻量 8 步两遍 | ✅ 可用 | ✅ | ✅ | ✅ |
| 标准 8 步两遍 ×1.5 | ✅ 慢 | ✅ | ✅ | ✅ |
| 精细 16 步 + easycache-av | ⚠️ 可跑但很慢 | ⚠️ | ✅ 推荐 | ✅ |
| 极致 20 步 + easycache-av | ❌ 不推荐 | ⚠️ | ✅ | ✅ 推荐 |
| 本地生图 4MP | ⚠️ 分钟级 | ⚠️ | ✅ | ✅ |
| 白模（SAM3DBody） | ✅ 25 帧约 16s | ✅ | ✅ | ✅ |
| 与生图/白模并发 | ❌ 显存不够 | ⚠️ | ✅ | ✅ |

耗时基线（**来源要看清，不要当成本机实测**）：

- 1344×768 / 10 秒 / 8 步两遍 ≈ **603s**（官方表格：4060 Ti 8GB + 64GB 内存）
- 本机 4060 8GB + 32GB 内存：无 H3 实测数据，按「内存少 32GB → 回读块更多」只会更慢，
  不写具体数字，界面上只说「十分钟量级」
- 白模 512×512 / 25 帧：首次 16s、热态 5.5s（本机实测）

### 4.4 越界时的处置（不静默截断）

超出画布/帧数上限时，在归一阶段就拦住，并给三条可执行出路：

1. 降画布（1344×768 → 1024×576，边长按 32 对齐）
2. 拆段续接（`continuation` 模式，末帧继承）
3. 降画质档（精细 → 标准 → 轻量）

理由：存档参数必须等于实际输出。用户要了 17 秒却拿到 8 秒，问题会被记到「引擎不稳定」上，
比直接拒绝更难查。
