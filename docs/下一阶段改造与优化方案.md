## 1. 建议先做什么

下一次实施只执行 **2A：数据库访问与事务边界**。它是任务恢复、审核原子性和资产保护的共同前提。先补足并发复现与事务失败回滚证据，再增加生成能力。

随后安排 **3A：数据保护门禁 → 2B：任务可靠性 → 2C：输入与产物适配**。将原批次 3 中的保护措施前置，是因为当前删除与审核路径仍可能破坏已制作成果；这部分应先于扩大生成和批量操作能力完成。

| 顺序 | 工作包 | 优先级 | 交付目标 |
|---|---|---|---|
| 1 | 2A 数据库访问与事务边界 | P0 | 并发请求不串事务，失败整体回滚，启动不静默清理旧数据 |
| 2 | 3A 数据保护门禁 | P0 | 审核失败不改变采用版本；被引用产物不可误删；导入预览不可过期提交 |
| 3 | 2B 任务可靠性 | P0 | 提交可追踪、重启可核查、重复事件不重复生成版本 |
| 4 | 2C 输入与产物适配 | P0 | 首尾帧实际可用，已有视频原样归档，前后端使用同一能力定义 |
| 5 | 3B 作品级资产与版本 | P1 | 固定角色/场景/剪辑引用，不因修改主记录而改变旧作品 |
| 6 | 4 预览与正式版体验 | P1 | 镜头入口与普通生成入口一致，成本和限制可解释 |
| 7 | 5 剪辑与导出优化 | P1 | 五镜头配音字幕成片，导出可预检、可复现 |
| 8 | 6 受限 AI 导演 | P2 | 先产生草案，人工批准后才提交受预算限制的任务 |

第一阶段的安装、升级、自有进程退出验收作为独立发布收尾工作。开发环境可继续上述改造；发布正式版本前必须补齐这些验收。

## 3. 下一次实施：2A 数据库访问与事务边界

### 范围与设计决定

先保留 SQLite 和现有表结构。采用现有共享连接的最小改造路径：所有数据库访问通过统一接口，并由同一把可重入锁保护完整查询及业务事务。将连接、游标结果读取、提交/回滚一起纳入边界，逐步消除业务模块直接使用 `db._conn` 的路径。

建议提供 `fetch_one`、`fetch_all`、单条写入、`transaction()` 等小接口；事务内部调用不得自行 commit。不要只给 `_row()` 加锁就宣称完成，必须覆盖跨多条语句的业务操作与返回记录读取。进入数据库事务前完成耗时文件检查；网络、模型推理、FFmpeg 和文件大批复制放在事务外。

Python 的 `check_same_thread=False` 允许跨线程访问，不会替应用定义业务事务的所有权；相关行为见 [Python 3.13 sqlite3 文档](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.connect)。SQLite 的线程串行模式也不等于多条业务语句自动原子化，见 [SQLite 线程模式](https://www.sqlite.org/threadsafe.html)。

本批次不切换 PostgreSQL，不引入完整 ORM，不重写推理引擎。后续若测量表明读锁成为瓶颈，再评估每请求/每线程连接；不在同一次修复中混用两种连接所有权模型。

### 任务清单

1. 在隔离库复现“项目创建/读取 + 音轨读取/修改 + 任务进度写入”的并发场景，记录请求、线程、异常堆栈和事务状态。日志不记录 API key、完整剧本或媒体内容。
2. 在 `db.py` 收口数据库访问和事务接口；改造 `storyboard.py`、`assets.py`、`tracks.py` 相关直接访问；统一显式事务策略，验证旧的 `BEGIN IMMEDIATE` 与嵌套调用不会冲突。
3. 将创建后读取、版本号分配、多步更新纳入同一业务边界。保证创建成功返回实际记录；异常返回明确错误并回滚，不用空对象或 null 掩盖失败。
4. 将启动孤立行处理改成只读审计/可恢复隔离。旧库启动不得先执行静默 DELETE；记录已存在的外键与级联行为，不增加新的破坏性级联。
5. 为需要修复的旧库先制作一致性备份，输出孤立记录清单和涉及的作品，另设显式修复操作；无异常库不得发生业务数据改写。
6. 显式设置并记录锁等待策略；数据库忙时返回可理解、可重试的响应。不得无限重试，也不得在不清楚提交结果时自动重放写请求。

### 候选文件与验收

修改位置：`backend/app/db.py`、`storyboard.py`、`assets.py`、`tracks.py`；按调用链必要性修改相应 router。拟新增 `backend/tests/test_db_concurrency.py`、`test_transactions.py`、`test_legacy_db_audit.py`，名称为规划，当前尚不存在。

建议验收负载为至少 10 个并发客户端、总计 1000 次混合请求；这是测试条件，不是已测吞吐承诺。要求无意外 500、成功创建不返回 null、成功写入数量准确、不出现事务串扰。用可控线程同步点复现交错，不能只靠一次随机压测。

在业务事务每个关键写入之后注入异常，恢复到操作前状态；外部读者看不到一半完成的数据。旧库升级/启动审计前后对比所有业务表，未选择修复的记录保持一致。

本批次完成后形成独立 commit 和 `docs/reports/phase2a.md`，附复现证据、测试命令、失败项及回滚演练。不在同一 commit 实现下列 3A/2B/2C。

## 4. 3A：先补数据保护门禁

这一包复用现有归属校验、QA、预览与事务导入，只补足保护边界。

| 操作 | 需要实现的行为 | 必须通过的反例 |
|---|---|---|
| 采用版本 | 检查镜头归属、受管路径、文件存在与可读、版本可用状态；采用后重新评估审核有效性 | A 镜头的版本不能给 B；缺失文件不能采用；新版本不能继承旧版本的 approved |
| 视频审核 | 先针对候选版本做只读 QA，提交时复核版本/revision，再原子写采用指针、审核状态与记录 | QA 失败时状态和 current_version_id 均保持原值；可追加 approve_blocked 诊断记录 |
| 删除任务/版本/素材 | 统一检查镜头、版本、时间线、导出快照和运行任务引用；先实现有引用即返回 409 和引用明细 | 从画廊删除已用于剪辑的视频，服务端拒绝；不能只在前端隐藏按钮 |
| 剧本重导入 | 预览返回内容哈希与项目 revision，提交校验；默认保留既有制作成果，破坏性重建必须有服务端确认与备份 | 预览后项目被修改则提交 409；注入失败时场景、镜头、剧本文本、时间线一起回滚 |

处理导入时先解决现有 `update_project(script=text)` 位于重建事务之外的问题。已有 append 会按场景标题跳过，并不是镜头级差异合并；UI 和文档应准确表达。旧 `script/import` 路由也必须执行服务端保护，不能依赖用户一定先调用预览。

本包先采用“引用则拒绝删除”，不同时开发完整回收站。后续 3B 再实现软删除、恢复和受控垃圾清理；磁盘清理必须以数据库引用及归档清单为依据，不能按文件年龄或目录通配符直接删。

时间线固定 `video_version_id` 到 3B 才交付。3A 的过渡保护是：镜头被时间线引用时，不得静默更换其 current_version_id；生成完成只增加候选，采用/指定版本审核/删除当前版本等路径若要改变该指针，先返回 409 和受影响片段明细。旧指针已经无效时提示修复，不能自动换成最新候选。这个阶段暂不提供“保留剪辑同时随意换采用版本”的能力，3B 完成后通过明确的替换剪辑操作解除限制。

## 5. 2B：任务可靠性与恢复

### 5.1 持久任务契约

在现有 jobs 上增量迁移或增加关联表，最终方案以迁移审查为准。所有旧路由继续工作，普通生成与镜头生成调用同一提交服务。

| 字段/关系 | 用途与约束 |
|---|---|
| `job_id`、`shot_id`、`project_id` | 稳定标识和归属；普通生成允许不属于作品 |
| `provider_id`、provider endpoint 标识 | 恢复时找回原服务；修改全局设置不得把旧任务查到另一台服务 |
| `request_snapshot` | 接受请求时固定模板副本、规范化参数和输入资产版本；生成的实际 seed 也固定保存 |
| `workflow_snapshot`、`workflow_hash` | 提交前保存最终节点图和规范化参数；排队后不再读取可变模板 |
| `client_id`、`provider_task_id` | 同一提交尝试的 HTTP/WS 使用相同 client_id；prompt_id 返回后立即保存 |
| `attempt_id` | 人工重试建立新尝试，拒绝旧尝试的迟到事件覆盖新结果 |
| `idempotency_key`、`request_hash` | 同一键和相同请求返回同一 job；同键不同内容返回 409，唯一性由数据库保证 |
| `input_asset_ids`、输入哈希、`output_asset_ids` | 固定实际输入与产出；快照不含 API key 等敏感配置 |
| `phase`、`last_reconciled_at`、结构化 `error` | 区分提交、执行、归档和待核查；错误包括阶段、原因、是否可重试 |
| `priority`、创建顺序 | 待执行任务持久排序，重启后顺序可复现；相同优先级按稳定序号 FIFO |

先保留 `status=pending/running/done/failed/cancelled` 的兼容投影，再通过 `phase` 和 `needs_attention` 表达精确阶段；更新 jobs store，使待核查不显示成“仍在正常生成”。不要在前端未适配时直接增加无人识别的状态字符串。

### 5.2 API 与调度兼容约定

以下为目标契约，尚未实现。继续保留现有 `/api` 前缀和响应主体类型，避免新增一套含义重复的生成入口。

| 接口 | 增量约定 |
|---|---|
| `POST /api/jobs`、`POST /api/shots/{id}/generate` | 可选 `Idempotency-Key` 请求头；新前端每次用户生成意图生成一个键，网络重试复用同一键；返回现有 job 对象并增补字段 |
| `GET /api/jobs`、`GET /api/jobs/{id}` | 保留旧 status；新增 phase、needs_attention、attempt 和 error；列表仍为数组，恢复程序使用内部数据库分页，不擅自改旧列表响应格式 |
| `POST /api/jobs/{id}/cancel` | 保留 ok 字段，同时返回请求是否被接受、取消阶段和最新 job；ok 不表示远端已经停止 |
| `POST /api/jobs/{id}/retry`（拟新增） | 仅对已明确失败/本地中断的任务建立新 attempt；已成功任务的重新生成走新 job；待核查任务不允许绕过确认盲目 retry |
| `PATCH /api/jobs/{id}/priority`（拟新增） | 仅可修改尚未领取的 queued 任务；已提交远端返回 409，不假称能够修改远端执行顺序 |
| `GET /api/providers/capabilities`（2C 新增） | 返回实际 provider、模式、输入槽位、取消能力和不可用原因；保留 `/api/engines` |

幂等键作用域定义为 NMVideo 本地服务实例中的 `(operation, target_id, key)`：普通生成 target 为全局生成入口，镜头生成为目标 shot_id，retry 为原 job_id。key 记录不可因任务结束立即删除；本阶段不自动淘汰这些小记录。相同键、相同请求返回原结果，同键不同请求返回 409。旧客户端不传键时，服务端为该次请求生成独立键，保留旧行为，但不能承诺两次 HTTP 请求被识别为同一次操作。

request_hash 基于规范化后的用户请求意图计算，不把每次随机生成的 seed 放入重复请求判定；实际 seed 只在第一次创建时生成并进入快照。人工 retry 使用新键建立新 attempt，重复发送该 retry 键只返回同一 attempt，不再增加尝试数；同一 job 不允许同时存在两个活动 attempt。结果仍不确定的任务，先完成服务端对账或明确的风险确认流程，再允许另建生成任务。

| phase / 情况 | 对外旧 status | worker 是否可领取 |
|---|---|---|
| queued | pending | 可以；需原子领取与优先级排序 |
| preparing / submitting / submitted / executing / collecting | running | 不可重新领取，继续原 attempt 或恢复处理 |
| recovery_required，或需核查的提交结果 | running + needs_attention=true | 不可领取；新 UI 明示需核查，旧 UI 只能看到 running 的兼容限制需在发布说明列出 |
| cancel_requested，已提交远端但尚未确认停止 | running | 不可领取，也不得自动重试 |
| cancel_requested，尚未提交远端 | cancelled（完成本地取消后） | 不可领取 |
| succeeded / confirmed_failed / local_interrupted / confirmed_cancelled | done / failed / failed / cancelled | 不可领取；人工 retry 须原子切换到新 queued attempt |

### 5.3 提交与对账规则

1. 在同一事务保存任务、request_snapshot、尝试、幂等信息及镜头排队关联，提交成功后才进入内存调度。
2. 以数据库任务为准领取待执行项；保持单 GPU 高负载任务并发 1。避免多个入口在“检查镜头状态”和“创建任务”之间产生竞态。
3. 准备阶段从 request_snapshot 构建执行图；若需上传输入，记录 provider 输入映射。在远端 POST 之前保存不可变的最终 workflow_snapshot、哈希和 submitting 阶段；HTTP/WS 复用预先生成的唯一 client_id，并携带本地关联标识（按服务能力支持）。2B 先覆盖现有文本工作流；2C 再提供完整上传和多槽位输入。
4. 提交超时或服务崩溃时先核查 queue/history。**client_id 是关联标识，不是服务端幂等承诺**；在远端不支持可靠防重时，不能承诺跨网络严格只执行一次。
5. 已知 prompt_id 时以 history 确认终态，以 queue 判断等待/执行；空 history、单次 404、临时不可达不能直接判定失败。
6. WS 与定时核查并行；即使 WS 连着但静默，也要按时核查。过滤不属于本 prompt/attempt 的消息；二进制预览与 JSON 状态分开解析，事件错误和连接错误分别处理。
7. 输出归档成功后，在同一数据库事务完成版本登记、任务完成和镜头状态更新；增加唯一约束，重复完成事件只产生一份版本。

2B 必须同时交付最小归档记录：基于现有 MP4 产物记录 attempt、最终文件位置、哈希、归档阶段和待登记元数据，提供可重入补登记。这样才能验证“文件成功、登记前崩溃”的恢复；不能把这个依赖推给后续 2C。2C 负责扩展原生视频结果类型、上传与作品目录适配，复用该归档协议。

建议初始参数：活跃任务每 3–5 秒核查一次，连续网络失败指数退避至不超过 30 秒；不确定状态超过可配置期限后转“需核查”，展示最近检查时间和手动操作入口。以上是待验证默认值；不把等候时长当作真实完成百分比。

### 5.4 重启和取消

| 重启时的情况 | 恢复动作 |
|---|---|
| 未提交的 pending | 从数据库分页恢复，不受固定 1000 条上限限制；按优先级/序号继续调度 |
| submitting，尚无 prompt_id | 用已保存关联标识核查；结果仍不确定则需人工确认，禁止盲目重复 POST |
| 已有 prompt_id | 查原 provider 的 queue/history；完成则补归档，仍排队/运行则继续观察 |
| 本地推理中断 | 明确“本地执行已中断，需重新生成”；不承诺断点续算 |
| 文件已归档、版本尚未登记 | 依据归档清单与哈希补登记，避免再次生成 |

取消待执行任务先持久标记并确保 worker 不再领取。已提交未运行时只删除目标 prompt 的远端排队项；执行中取消优先使用已验证的定向取消能力。当前客户端不带 ID 调用 `/interrupt`，可能影响共享 ComfyUI 的其他任务，必须消除这一默认行为。

如果安装的服务仅支持全局 interrupt，默认不发送它；说明“无法安全停止远端执行”，保留取消意图并继续核查，完成后不自动采用。取消是请求与确认两个阶段，不能收到本地点击就虚报远端已经停止。

ComfyUI 上游目前存在上传、队列管理、历史和取消相关接口，但部署版本与自定义节点可能不同；实施时记录实际 ComfyUI commit/版本并验证能力，不直接套用 master。接口依据见 [ComfyUI server.py](https://github.com/Comfy-Org/ComfyUI/blob/master/server.py)。

候选文件：`comfyui.py`、`engines/comfy.py`、`queue_manager.py`、`db.py`、`storyboard.py`、jobs/storyboard router、`frontend/src/store/jobs.js`、队列视图。

## 6. 2C：输入可用与产物原样归档

### 能力校验与输入上传

- 新增 provider 能力结果，至少区分 t2v、i2v、首尾帧、多参考、续接、可否安全取消。服务在线不等于模型与节点已安装，也不等于支持当前模板。
- 前后端使用同一能力定义。不支持的选项显示原因并禁用；服务端也要拒绝，不能静默忽略参考图。
- 将首帧、尾帧、角色参考图拆成明确的输入槽位。首尾帧模式必须同时验证两个槽位与节点映射；缺少任何一项直接阻断。
- 参考输入先解析到受管资产，检查路径边界、文件类型/大小/存在性和哈希，再调用 ComfyUI 上传接口，使用它返回的名称/子目录注入。仅明确配置共享目录时才使用路径映射。
- 续接记录来源镜头、来源版本、输入末帧资产。前段更新只标记下游待检查，不覆盖或销毁下游结果。

### 输出归档

让 provider 返回可区分的 `video` / `frames` 结果：原生视频直接下载并保留，图片序列才合成视频。可在现有 BaseEngine 上加结果适配层，保留本地引擎原帧序列路径，不要求一次重写全部引擎。

原文件写入临时文件，验证长度、可解码性和 SHA-256 后原子重命名；同一文件系统内发布完成文件。保留实际容器与扩展名，不把 GIF 等输出一律命名为 MP4。单独生成封面和播放代理，不让它们替代原文件。

建议新增作品级目录，而非移动已有全目录：`outputs/projects/{project_id}/shots/{shot_id}/generations/{job_id}/{attempt_id}/`。普通生成继续使用独立 job 目录；旧作品原路径继续可读。元数据记录工作流哈希、输入/输出哈希、provider 与版本。文件系统和 SQLite 之间不能靠一个 SQL 事务完成原子提交，需有归档清单、可重入收尾与孤立文件核查流程。

## 7. 后续产品与性能优化

| 方向 | 下一步具体优化 | 前置条件/收益验证 |
|---|---|---|
| 作品资产版本（3B） | CharacterVersion/EnvironmentVersion 及快照；时间线固定 video_version_id；旧时间线回填当前版本并保留追踪信息 | 3A 完成；改角色或重新采用镜头版本后，旧任务和已编辑片段保持可解释 |
| 生成参数一致（4） | 共用参数规范化；provider 单独定义预设；同一请求从两个入口产生一致实际参数 | 2B/2C 完成；测试 preset、显式参数、preview 的优先级，旧 seed 不被悄悄替换 |
| 预览转正式版（4） | 保留两个版本，记录来源版本、prompt/seed/参数和角色快照；无原生二采能力时标明“重新生成正式版” | 不承诺同 seed 必得完全一致视频；记录模型、工作流及运行配置支持追溯 |
| 进度与轮询 | 只对活跃任务持续刷新；合并重复的 jobs/engines 请求；页面隐藏时降低频率，恢复可补状态 | 先测请求数与状态延迟；保留对账，不把轮询优化成无法恢复的纯 WS |
| 数据查询 | 消除项目列表逐项目 COUNT 查询；检查 jobs 状态/排序、项目场景/镜头和版本关联索引 | 根据 EXPLAIN QUERY PLAN 与样本库决定索引；不盲目给所有字段加索引 |
| SQLite 性能 | 正确性稳定后评估多连接/WAL、锁等待和 checkpoint；保持短写事务 | WAL 仍只有一个写者，也不适合网络文件系统；依据 [SQLite WAL 文档](https://www.sqlite.org/wal.html) 测试后决定 |
| 视频处理 | 原生视频不走抽帧重编码；缓存媒体探测和封面；仅导出需要统一规格时转换 | 对比 CPU 时间、磁盘峰值、输出哈希/质量与音轨是否保留 |
| GPU/内存 | 默认单 GPU 任务；按真实显存和模型可用性显示预设；明确 OOM、缺模型与服务离线区别 | 在目标 RTX 4060 8GB 实测；不能用 mock 或别的显卡结果代替 |
| 剪辑导出（5） | 导出前检查缺文件、裁剪范围、时长/帧率/音频、字幕；导出绑定不可变时间线快照 | 五镜头配音/音乐/音效/字幕 MP4；导出中编辑项目不改变已提交导出 |
| AI 导演（6） | Schema 校验的镜头草案、逐任务确认、每日/项目预算、有限重试和取消后不自动重提 | 前述任务与资产基础可靠后再做；禁止先扩展自动提交能力 |

衡量优化前后时记录统一样本、软件版本、冷/热启动和硬件信息，至少记录 p50/p95 请求耗时、请求数、锁等待、峰值显存/内存、生成/归档/导出分段耗时。不预设没有测量依据的“提速百分比”。

### 迁移与恢复

2A 尽量不改业务表；2B/3A/3B 的新增字段、索引和关系须使用带版本号、可重复检查的迁移。先检查重复键/非法引用再建唯一约束，不能为了索引成功而静默删记录。历史任务缺少工作流快照时标记“历史参数不完整”，不能伪造原始工作流。

迁移前停止写入，使用 SQLite 一致性备份并保存作品文件清单、哈希、schema 版本；备份流程依据 [SQLite Backup API](https://www.sqlite.org/backup.html)。恢复演练须对比表结构、行内容和关键文件，不只检查数据库能打开。切换 WAL 后也不能在有写入时只复制主 `.db` 文件。

回滚必须先停止服务和全部写入者，独立备份改造后的完整数据库，以及期间新增/修改的实际媒体文件和必要配置，记录其任务/作品/资产对应关系并验证备份可恢复。只有清单与哈希而没有文件副本不能恢复数据。

再恢复匹配旧代码、旧数据库和旧文件的同一快照。改造后的新增数据保留在独立快照，不自动塞回旧库；需要带回时另行设计兼容导入。**git revert 不能替代数据回滚**；旧版本不理解新字段/状态时，不得直接运行旧程序继续写新库。

### 第一阶段发布收尾

1. Windows 安装/卸载向导、安装目录无写权限、升级后项目与配置保留。
2. 实际启动自有 launcher 后退出，确认自有子进程清理；复用外部后端/ComfyUI 时退出不终止它们。
3. 有可用测试发布时验证更新检查、下载、安装、失败恢复；当前历史记录为无发布版本，尚未验收完整更新链。
4. 验证开发版与安装版的外链、媒体资源、日志复制、错误/等待/重试入口。前端 CSP 以实际资源清单分阶段收紧，避免阻断现有素材。
5. 每包提交独立 commit、真实测试输出及报告；安装包标明对应 commit。无条件测试和真实 GPU/安装测试分开记录。
